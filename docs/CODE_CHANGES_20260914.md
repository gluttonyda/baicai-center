## 主要行为差异

## 数据库与协议 v2

`SCHEMA_MINIMAL.sql` 面向新建数据库；已有数据库使用以下迁移顺序，并先核对当前表结构：

1. `MIGRATION_SPLIT_ACCOUNT_LOCKS.sql`：拆分账号执行锁和配额锁。
2. `MIGRATION_UPLOAD_USAGE_STATS.sql`：补充文件大小及 `account_upload_events`。
3. `MIGRATION_DISPATCH_PROTOCOL_V2.sql`：补充协议、租约及来源指纹。

协议 v2 迁移会增加或确认以下结构：

| 表 | 主要变化 | 用途 |
| --- | --- | --- |
| `worker_registry` | `protocol_version` | 调度器只向声明 v2 的活跃节点派发新任务 |
| `drive_accounts` | `current_dispatch_id`、`current_worker_node`、独立调度冷却字段与索引 | 识别租约归属，分别表达执行占用、调度冷却、配额封禁 |
| `file_tasks` | `source_base_dir`、`source_mtime`、`dispatch_id` 及索引 | 记录文件来源和指纹，将回执限制到相应批次 |
| `account_upload_events` | `dispatch_id`；唯一键改为 `(file_task_id, dispatch_id)` | 同批次重复回执只记一次；文件经新批次再次成功可以重新记账 |

账号锁和 v2 迁移通过 `information_schema` 检查字段和索引是否存在，上传统计迁移也检查已有结构，可以重复执行。MySQL DDL 可能隐式提交，因此迁移不是整体可回滚的事务；执行前应备份，并在目标 MySQL 8.x 环境验证。生产专用的一次性账号路由脚本不在通用迁移链中，不应据此重置账号封禁或人工停用策略。

`file_path` 的哈希仍是全局目标身份。增加 `source_base_dir` 用于找到正确的本地来源，不会把不同根目录的同名目标自动拆成多个独立任务。

Center 和 Worker 双向请求都支持 HMAC 签名。`WORKER_TOKEN_MAP` 保存各节点密钥映射，节点使用对应的 `NODE_TOKEN`；模板建议至少 32 个随机字符。时间戳检查依赖节点时钟同步。历史快照导入也使用节点签名。

`ALLOW_LEGACY_NODE_AUTH`、`ALLOW_LEGACY_UNLEASED_REPORTS`、`ALLOW_LEGACY_BEARER_AUTH` 和 `SCANNER_SEND_BEARER_AUTH` 仅用于有计划的升级过渡；它们不替代新任务对协议 v2 的要求。

## 暂停、重启与回执恢复

Worker 收到新批次后先持久化 journal，再启动任务。相同 `dispatch_id` 和相同内容的重复请求返回已接收；相同 ID 携带不同内容会拒绝。最终回执发送失败时保留在 journal 中，后台继续补送。

重启恢复调用 `/api/dispatch/validate`。仍归属于本节点、账号和批次的任务可以继续；过期或已改派的任务取消。执行期间发现失去租约，会终止对应旧 rclone。已取得租约的恢复任务不受后来降低的入场并发上限阻挡，避免重启造成任务遗留；新的任务仍按当前上限接收。

普通重启必须保留 `TASK_JOURNAL_DB_PATH` 对应的持久卷。清理 Scanner 去重缓存与删除任务 journal 是不同操作；只有完整重置 Center 数据后才需要考虑重建扫描缓存。

## Scanner、路径与文件版本

Scanner 支持普通链接目录、缓存链接目录和 rclone 缓存目录，分别通过配置设置等待时间和 `copy`/`move` 策略。rclone 缓存仍需要通过大小与修改时间的稳定窗口检查。

上报包含相对路径、大小、修改时间和来源根目录。若同一路径已有活跃上传或中转任务，Center 保留当前任务指纹，并把尚未接纳的新观测列入 `deferred_files`；Scanner 不将这些观测记为已经成功同步。已完成文件的已知指纹变化可以重新排队。

Worker 上传前核验来源目录白名单以及预期大小、修改时间。派发后已变化的文件不按旧版本直接上传。`move` 任务本地文件已消失时，通过远端列表和已有指纹复核成功结果，查询失败或指纹不匹配不会补记成功。

扫描与历史同步保留文件名的 Unicode 形式，路径字段保留合法首尾空格，并拒绝换行、回车和空字符。Worker 继续进行规范路径和符号链接越界检查。

暂时不可见的文件回报 `not_found` 后，Center 可按 `NOT_FOUND_RETRY_MINUTES` 自动重新排队。该机制提供重试，不会自动推断目录迁移前后的路径映射；变更挂载和扫描根目录时仍需保持两端配置一致。

## 路由、并发与错误处理

`STAGING_REMOTE_DIR` 控制普通中转及新直传组的根目录，`LEGACY_DIRECT_REMOTE_DIR` 控制旧直传组的根目录，`CLEANER_DEST_REMOTE` 指定最终目标 remote。直传成功进入 `completed`，普通中转上传成功进入 `staged`。账号类型识别仍依赖代码约定的命名前缀，更换命名约定时应同步调整并运行路由测试。

跨共享盘 cleaner 操作读取目标 remote 的共享盘标识，但继续使用源 cleaner 凭据访问源文件；相应凭据需要具备两端访问权限。cleaner 与同组 uploader 的租约互斥，失败后可进入独立调度冷却，并支持通过 `CLEANER_DISPATCH_ENABLED` 控制定时派发。

Center 和 Worker 默认在北京时间 01:00–10:00 允许每节点 3 个 uploader，其他时段为 2 个，均可配置。`RCLONE_TRANSFERS` 和 `RCLONE_CHECKERS` 默认分别为 4 和 8；`RCLONE_BWLIMIT` 仍是单个 rclone 进程的限制，不是节点总带宽限制。新入场限制不会主动终止已经执行的任务。

Worker 通过日志特征和退出码区分 `credential_invalid`、`403_quota` 与普通 `failed`。凭据失效会触发账号停用，重新授权后仍需验证并恢复启用状态；普通失败不再无条件触发 24 小时封禁。配额/限流分类仍依赖日志标记，不是对 Google 实际配额余额的查询。失败批次中已成功文件先更新，再处理剩余任务与租约。

## 上传统计口径

`GET /api/upload_usage` 默认统计最近 24 小时，包含零上传记录的 uploader，并附带当前启用状态、有效锁及解锁时间。多种锁同时存在时，自动可用时间取有效锁的最晚时间；人工停用账号没有自动解锁承诺。`GET /api/upload_usage/daily` 按北京时间日期汇总。

容量来自数据库中成功事件对应的文件大小，不是网卡流量或 Google 官方剩余额度。重试传输的字节、尚未成功回报的文件和大小未知的历史任务可能不反映在这一数字中；相同文件在新 dispatch 中再次成功也会形成新的事件。数据库时间使用 UTC，对外提供北京时间字段。
